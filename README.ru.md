# cursor-bridge

🇬🇧 [English version](README.md)

Если вы платите и за Claude Code, и за Cursor, то наверняка замечали неловкую вещь: всю работу делает Claude, а подписка Cursor тихо продлевается каждый месяц и в основном простаивает.

cursor-bridge это исправляет. Это MCP-сервер, который отдаёт headless `cursor-agent` от Cursor в руки Claude Code как **вторую AI-рабочую силу** — которой Claude может делегировать задачи, с которой может спорить и которую может использовать как независимого проверяющего. Это не игрушечная интеграция: каждая задача работает под watchdog-таймерами, git-предохранителями и локальной телеметрией — потому что весь смысл в том, чтобы результатам можно было доверять.

## Идея в одной истории

Допустим, Claude только что отревьюил ваш код и нашёл пятнадцать подозрительных мест. Что дальше? Можно прочитать все пятнадцать самому — минус вечер. Можно поверить на слово — но примерно четверть находок AI-ревью оказывается ошибочной, и вот вы уже «чините» код, который был исправен.

А можно сделать то, что делает этот проект: отдать находки **другому семейству моделей** и заставить две противоборствующие роли драться за каждую. *Прокурор* доказывает, что баг настоящий — прослеживает путь по коду до самой поломки. *Адвокат* доказывает, что это ложная тревога — ищет защитную проверку, лок, задокументированное проектное решение, которое ревьюер не заметил. Когда они сходятся — с цитатами кода, которые сервер буквально сверяет с вашими файлами, — дело закрывается автоматически. Когда спорят — оно ложится к вам на стол. В итоге вы читаете три спорных находки вместо пятнадцати.

Эта философия проходит через весь проект: **автоматизируется труд верификации, но никогда — право финального вердикта.**

## Что внутри

Один сервер, тринадцать инструментов, три механизма. Представьте ящик с тремя отделениями.

### Отделение первое: делегирование

Хлеб с маслом. `cursor_run` запускает асинхронную задачу Composer'а в любом репозитории — массовые правки, кодмоды, бойлерплейт, каркасы тестов, вся механика, которая съедает день. `cursor_ask` — для быстрых вопросов, `cursor_reply` продолжает разговор с тем же агентом. Параллельно работают до трёх задач, и модель можно выбирать на каждый вызов свою.

К праву на запись отношение серьёзное: правящая задача либо требует чистого git-дерева, либо получает собственный изолированный git worktree. Если что-то пойдёт не так — ваша работа не пострадает.

### Отделение второе: сыщики

`cursor_review` — адверсариальное ревью любого артефакта: спеки, плана, диффа, модуля. Приём, на котором всё держится: ревью **никогда не бывает одним ревьюером**. Два-три параллельных ревьюера с намеренно разными характерами читают одно и то же, не видя друг друга. Для документов это *broad* (внешние риски и слепые зоны), *strict* (внутренняя строгость, холодный экзаменатор) и *hygiene* (тесты, которые пройдут на сломанном коде). Для кода — *correctness*, *security* и *tests*, всегда все три.

Разные характеры действительно находят разное, а отчёт о пересечениях показывает, где они сошлись — обычно именно там и горит.

### Отделение третье: следователи

`cursor_refute` — новейший механизм, тот самый из истории выше. Вы отдаёте ему папку находок — до двенадцати по одному участку кода — и пара «прокурор/адвокат» берётся за работу. Дальше сервер применяет намеренно асимметричное правило:

- **Авто-подтверждение** — только когда обе роли сказали «настоящий», и обе цитаты прошли проверку.
- **Авто-закрытие как ложного** — только когда обе сказали «ложная тревога», и обе цитаты прошли проверку. И даже тогда запись хранится вечно и никогда не удаляется: опровергнутая находка — тоже результат.
- **Всё остальное — к вам**: споры, неуверенность, не сошедшаяся цитата, погибшая или обленившаяся роль.

«Прошедшая проверку цитата» — это буквально. Процитированный код обязан реально существовать в указанном файле, в пределах двадцати строк от указанной строки, быть содержательным (забор из `////////` ничего не доказывает), лежать в отслеживаемом git'ом файле и сопровождаться собственным рассуждением. Сервер к тому же пинует состояние вашего дерева между стартом и финишем: если HEAD уехал или дерево испачкалось — все авто-вердикты отменяются, потому что вердикт о коде, который под ним поменялся, не стоит ничего.

## С чего начать

Понадобятся три вещи:

- **Node.js 26+** — сервер исполняет TypeScript нативно, этапа сборки нет вообще;
- **[cursor-agent CLI](https://cursor.com/cli)**, установленный и залогиненный (`cursor-agent login`), с активной подпиской Cursor;
- **Claude Code** — или любой другой MCP-клиент, умеющий stdio-серверы.

Дальше:

```bash
git clone https://github.com/toxmost/cursor-bridge.git
cd cursor-bridge
./install.sh
```

Установщик проверит окружение, поставит зависимости, зарегистрирует сервер в Claude Code (user-scope — будет доступен в каждом проекте) и положит опциональный **скилл cursor-delegate** — плейбук, который учит Claude, когда тянуться к какому отделению, чтобы вам не запоминать имена инструментов. `./install.sh --no-skill` — без скилла, `--uninstall` — убрать всё.

Одна вещь, о которой стоит помнить: уже открытые сессии Claude Code держат старый набор инструментов. После установки откройте новую.

## Как это выглядит в работе

В основном вы просто разговариваете с Claude:

> «Отдай Composer'у: добавь JSDoc всем экспортируемым функциям в src/.»
>
> «Дай второе мнение по docs/design.md, прежде чем я начну это строить.»
>
> «Вот пять находок из ревью — перепроверь их по коду.»

Скилл сам разведёт запросы по механизмам. А если хочется звать инструменты напрямую — вот как выглядит папка на верификацию:

```jsonc
// cursor_refute
{
  "findings": [{
    "id": "B-001",
    "title": "бонус списан, а обновление заказа может упасть",
    "file": "src/pay.ts", "line": 42, "severity": "S1",
    "claim": "spendBonus проходит, затем updateOrders бросает — деньги списаны, скидка не записана"
  }],
  "cwd": "/абсолютный/путь/к/репо",
  "context": "модуль платежей; запиненный read-only worktree",
  "domain": "orchestration"   // потом позволит считать долю ложных опровержений по доменам
}
```

Поллите `cursor_refute_result` (умеет long-poll через `wait_sec`) — получите вердикты обеих ролей по каждому делу, свод и счётчики: авто-подтверждено / авто-закрыто / эскалировано.

## Почему этому можно доверить настоящую работу

Несколько выстраданных проектных решений — за каждым стоит реальный инцидент времён разработки:

- **Три отдельных бюджета watchdog'а на задачу** — жёсткий таймаут, грейс «до первого токена» (модель, думающая пять минут перед ответом на тяжёлом ревью, — это норма, а не зависание) и детектор межтокенного застоя. Известный баг вечного зависания `cursor-agent -p` обезврежен конструкцией, а не надеждой.
- **Read-only значит read-only.** Ревью и верификация работают в режиме ask — они физически не могут менять ваши файлы.
- **Каждый результат несёт `verify_note`** — напоминание любому читателю, человеку или AI: выдача субагента — непроверенное утверждение, пока не сверено. Звучит занудно ровно до первого раза, когда агент вкатит ошибочную находку прямо в спеку.
- **Всё остаётся локально.** Журналы задач и телеметрия живут в `jobs/` и `logs/` внутри репозитория, оба в gitignore. С машины не уходит ничего, кроме того, что сам `cursor-agent` шлёт в API Cursor.
- Одна честная оговорка: **промпты видны в локальном `ps`** — не кладите секреты в брифы.

## Структура проекта

```text
src/            сервер: менеджер задач, watchdog'и, git-предохранители, движки ревью и верификации, телеметрия
skills/         скилл cursor-delegate для Claude Code
tools/audit/    автономные помощники картирования больших репо перед систематическим аудитом кода
test/           285 тестов (node:test), включая e2e-обвязку с поддельным агентом
```

Разработка освежающе скучна: `npm ci`, потом `npm test`. Ни сборки, ни бандлера, ни конфигов.
